# Feishu Progress Card Size Budget and Limit Recovery

## 背景

飞书 CardKit JSON 2.0 对卡片实体有两类关键硬限制：序列化后的卡片体积需要控制在 30KB 内，超限返回 `200860`；一张卡片最多支持 200 个元素或组件，超限返回 `300305`。当前进度卡对每次工具调用固定展示 300 字符输入和 700 字符输出，同时最多保留 30 次工具调用。这些固定字符数不是飞书 Markdown 组件的硬限制，单条工具详情偏短；另一方面，30 条中文工具详情即使按 300/700 截断，仍可能显著超过 30KB。

当前恢复逻辑只识别 `300305` 和特定英文错误文案，把组件数超限笼统视为卡片大小超限，并在更新失败后直接换新卡片。它没有覆盖真正的体积超限错误 `200860`，也没有在换卡前优先删除旧过程、保留最新信息。

## 用户目标验证清单

### 必须实现

- 放宽最新工具详情的信息量，不再把 300/700 当作平台硬限制。
- 在请求飞书前按卡片 JSON 的 UTF-8 序列化字节数和组件数主动执行预算裁剪。
- 超预算时优先删除最旧过程记录，始终保留最新过程，并在卡片内提示省略数量。
- 分别识别 `200860` 卡片体积超限与 `300305` 组件数超限。
- 服务端返回限制错误后，使用更严格预算重建并重试当前卡片；仍失败时降级为精简卡片，最后才换新卡片。
- snapshot 保留完整运行历史，裁剪只作用于飞书渲染视图，避免影响 Web UI、日志和后续状态计算。
- Codex 运行时在顶部状态区展示本 session 累计 Token、任务耗时和 7 天额度窗口的剩余百分比；展开后展示已用百分比和重置时间。

### 必须不破坏

- 顶部状态、计划、最新运行状态和底部最终结论保持可见。
- 现有 `sequence` 严格递增、UUID 幂等、流式关闭和失效 card ID 恢复逻辑保持有效。
- 非限制类网络、权限或参数错误不得被误判为可裁剪重试。
- 精简模式仍能继续更新最新进展和最终结论。
- 动态元素 ID 继续满足 20 字符、字母开头且卡片内唯一的限制。

### 必须真实验证

- 单元测试证明 ASCII、中文和 JSON 转义后的预算按序列化字节计算，而不是 Rust 字符数。
- 单元测试证明裁剪顺序为最旧到最新，最新工具详情和最终输出不会被旧记录挤掉。
- mock CardKit 链路分别返回 `200860`、`300305`，验证更严格预算重试成功。
- mock CardKit 链路连续拒绝完整卡片时，验证精简卡片接管且后续仍可更新。
- human_tests 按真实卡片 JSON 和 mock API 请求逐条验证正常、边界和降级场景。

### 必须交付

- 同步代码、单元测试、E2E、human_tests 与索引。
- 完成至少两轮 Review/Fix/Test。
- 推送功能分支、创建 PR，并由远端 coverage 90% 与全部 CI 门禁兜底。

## 设计原则

1. **保新去旧**：运行中的最新工具、最近模型说明和最终结论比早期详细日志更有操作价值。
2. **完整状态、有限历史**：snapshot 是完整事实源；飞书卡片只是受限的投影视图。
3. **主动降级优先于失败恢复**：正常请求应留出安全余量，不把飞书错误当常规分页机制。
4. **服务端错误仍是最终事实**：本地预算不能替代平台校验，必须保留错误驱动的二次收缩。
5. **降级可感知**：用户需要知道旧过程被省略，不能无提示消失。
6. **资源口径诚实**：周额度来自 Codex app-server 的 10080 分钟窗口，只展示百分比，不伪造剩余 Token 数；协议无数据时不展示占位假值。

## Codex 资源指标

- 启动 Codex app-server 并完成初始化后，调用只读 `account/rateLimits/read` 获取初始快照；不支持该方法的旧版本仅记录 debug 日志，不阻断任务。
- 合并运行期间的 `account/rateLimits/updated` 稀疏通知。只有 `windowDurationMins == 10080` 的窗口才认定为周额度，避免把短时窗口或 API RPM/TPM 限流误标为周额度。
- 额度响应进入 progress/session 事件前只投影 `usedPercent`、`windowDurationMins`、`resetsAt`；不持久化 credits、plan 或账号字段。
- `usedPercent` 转换为 `100 - usedPercent` 的周余额，并限制在 0% 到 100%；`resetsAt` 按运行 Bifrost 的本地时区展示。
- `thread/tokenUsage/updated.tokenUsage.total.totalTokens` 是当前 Codex thread/session 的累计 Token，直接展示为“本次 Token”；输入、输出、缓存输入和推理输出仍在展开详情中显示。
- 顶部折叠标题采用“Runner / 模型 / 本次 Token / 周余额 / 耗时”的紧凑顺序；无周额度或 Token 数据时省略相应段落，不显示误导性的 0。

## 预算与展示策略

### 标准模式

- 本地安全预算：序列化卡片 JSON 不超过 24KB。
- 本地组件安全预算：不超过 180 个 `tag` 元素/组件。
- 单个工具输入预览：最多 1000 个 Unicode 字符。
- 单个工具输出预览：最多 3000 个 Unicode 字符。
- 默认最多考虑最新 30 次工具调用；若整体仍超预算，继续从最旧 timeline item 开始删除。

24KB 和 180 个组件分别为飞书 30KB、200 组件硬限制预留 JSON 转义、平台内部转换和后续状态更新余量。字符截断仅用于限制单个异常工具，最终是否可发送以完整 JSON 字节预算为准。

### 收缩重试模式

- 服务端返回 `200860` 或 `300305` 后，将预算降至 16KB、120 个组件。
- 重新从完整 snapshot 生成视图，删除更多旧过程，但保留最新 timeline item。
- 使用完整卡片更新接口重试当前 card entity，避免立即产生额外消息。

### 精简模式

- 收缩重试仍被飞书拒绝时，使用现有精简卡片结构。
- 精简卡片保留状态、明确的降级说明和最多 1000 字符的最新/最终输出，不携带工具详情。
- 精简模式成功后，本 card entity 后续保持精简，避免状态在完整/精简之间反复抖动。

### 最终换卡

- 只有当前 card entity 的精简更新也失败，才沿用现有 rollover 创建新卡片。
- 新卡片创建同样先走标准预算、收缩预算、精简模式，不能重复发送同一个超限 payload。
- 冻结旧卡片属于 best effort；冻结失败不能覆盖新卡片已经成功发送的事实。

## 渲染算法

1. 克隆 `ImAgentProgressSnapshot` 作为只读渲染视图。
2. 按最新 30 次工具调用确定初始时间线窗口。
3. 构建完整 CardKit JSON，使用 `serde_json::to_vec` 计算真实 UTF-8 字节数，并递归统计带 `tag` 的元素/组件数量。
4. 若任一预算超限，从视图中删除最旧 timeline item，累计省略数并重新渲染。
5. 至少保留最新一条 timeline item；首行插入“已省略前面 N 条过程记录，仅保留最新内容”的状态说明。
6. 如果只剩最新过程仍无法满足预算，返回精简卡片。
7. 原始 snapshot、tool logs 和最终输出不被修改。

## 错误分类与恢复状态机

```text
标准预算完整卡片
  ├─ 成功 → 继续标准模式
  ├─ 200860 / 300305 → 收缩预算完整卡片，重试当前实体
  │    ├─ 成功 → 后续保持收缩预算
  │    └─ 再次限制错误 → 精简卡片，重试当前实体
  │         ├─ 成功 → 后续保持精简模式
  │         ├─ 再次限制错误 → rollover 新卡片
  │         └─ 普通网络/权限/参数错误 → 原样返回，不创建重复消息
  └─ 其他错误 → 不裁剪、不吞错，直接返回
```

`200860` 与 `300305` 都允许进入相同的收缩流程，但日志必须保留具体分类，便于判断是内容体积还是组件结构导致。

## 测试方案

### 单元测试

- 标准短卡片不裁剪，最新工具输入可超过旧 300 字符限制，输出可超过旧 700 字符限制。
- 30KB 级 ASCII/中文/带转义内容按 JSON 字节预算触发裁剪。
- 多条过程只删除最旧项，保留最新工具 marker，并显示准确省略提示。
- 组件数量超过安全预算时同样裁剪。
- `200860`、`300305` 被识别为不同限制类型；普通 `10002`/网络错误不匹配。
- 最终输出本身过大时进入精简模式，避免无限裁剪循环。

### E2E / mock CardKit

- 第一次全量更新返回 `200860`，第二次 payload 更小、不含最旧 marker、仍含最新 marker，并在同一 card entity 更新成功。
- 第一次返回 `300305` 时执行同样的收缩重试。
- 完整卡片连续两次被拒绝后，第三次 payload 为精简卡片；随后新事件继续更新同一卡片。
- 非限制错误只请求一次并透传失败。

### human_tests

在 `human_tests/feishu-progress-card.md` 新增专项用例，使用真实渲染 JSON 与 mock Feishu API 验证：

- 长输入/输出比旧版展示更多，但卡片 JSON 保持在安全预算内。
- 长任务只省略旧过程，最新工具和结论仍可展开查看。
- `200860`/`300305` 自动收缩重试无额外消息；连续失败进入精简卡片。

## 风险与取舍

- 飞书公开文档以 30KB 描述卡片体积，没有明确内部序列化口径；24KB 安全水位是主动保守值，服务端重试仍是必要兜底。
- 同一失败更新的 sequence 是否被平台消费没有明确说明。实现继续单调递增 sequence，避免复用旧 sequence；mock 和真实链路需要重点观察 `300317`。
- 删除旧 timeline 会减少历史可见性，但完整历史仍保存在 snapshot/运行记录中；卡片明确展示省略提示。
- 最新工具详情最多约 4000 字符，极端情况下仍可能触发精简模式，但不会牺牲更新链路可用性。
