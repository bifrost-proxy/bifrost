# Bifrost Resolver 两相改造技术方案

## 问题定义

当前 `RulesResolver::resolve()` 把 pattern 匹配、filter 决策、模板展开揉在一个循环里，整体结果以 `url|host|path|method` 为 key 缓存。当多条规则匹配同一 URL 但靠 request header filter 分流时，缓存 key 不含 header → 第一次解析结果被复用 → 后续不同 header 的请求永远走第一条规则 → header 路由失效。

典型场景：
```
www.coze.cn host://127.0.0.1:3000 includeFilter://h:x-tt-env-fe=featA-web
www.coze.cn host://127.0.0.1:3001 includeFilter://h:x-tt-env-fe=featA-mobile
```
第二条规则在缓存生效后永远不会被选中。

## 根因

`crates/bifrost-core/src/rule/resolver.rs:258`:
```rust
let cache_key = format!("{}|{}|{}|{}", ctx.url, ctx.host, ctx.path, ctx.method);
```

cache_key 假设「同 URL+method → 同解析结果」，但 filter 的决策依赖 header/cookie/ip 等请求动态信息。

## 设计原则

- 缓存应该覆盖「确定性只依赖 URL 的计算」（pattern matcher），不应覆盖「依赖请求动态上下文的决策」（filter gate）
- 无 header filter 的规则集性能不回退
- 最贵的 matcher 匹配（正则/通配符）仍然缓存
- filter 比较本身很便宜（字符串比较），不缓存无影响

## 架构设计：两相 Resolve

### Phase A — Matcher Candidates（可缓存）

**输入**: url, host, path
**输出**: `Vec<CandidateMatch>` — pattern 命中的候选规则（按优先级排序）
**Cache key**: `url|host|path`（不含 method/header）
**Cache 类型**: `LruCache<String, Vec<CandidateMatch>>`

```rust
struct CandidateMatch {
    rule_index: usize,
    captures: Option<Vec<String>>,
    is_negated: bool,
}
```

Phase A 只做 `rule.matcher.matches(url, host, path)` —— 最贵的正则/通配符运算。不评估 filter、不做 first-match-wins 判断、不展开模板。

### Phase B — Filter Gate + Decision（不缓存，每请求执行）

**输入**: Phase A 候选 + 完整 RequestContext（header/cookie/ip/method/status）
**输出**: 最终 `ResolvedRules`

逻辑（对候选逐条）：
1. 跳过 disabled 规则
2. 处理 negated 规则（标记 matched_protocols）
3. 非 multi_match 且协议已命中 → skip
4. **评估 include_filters → 不过则 continue**
5. **评估 exclude_filters → 命中则 continue**
6. skip 决策
7. 通过以上 → `ResolvedRule::new`（含模板 `${reqH...}` 展开）→ `result.add`
8. 非 multi_match → 标记 matched_protocols

**关键**：`matched_protocols`（first-match-wins）的判定在 Phase B，因为"第一条是否生效"取决于它的 filter 是否通过。如果第一条被 filter 否决，第二条有机会。

### 为什么 method 不进 Phase A cache key

- Filter 里有 `Filter::Method`（`includeFilter://m:GET`），这属于请求动态上下文
- Pattern matcher 本身不看 method
- 如果进 key 会降低 Phase A 缓存命中率
- 放到 Phase B filter gate 统一处理

## 伪代码

```rust
pub fn resolve(&self, ctx: &RequestContext) -> ResolvedRules {
    // Phase A: 候选解析（带缓存）
    let candidates = self.get_matcher_candidates(ctx);

    // Phase B: filter gate + 决策（不缓存）
    self.apply_filter_gate(&candidates, ctx)
}

fn get_matcher_candidates(&self, ctx: &RequestContext) -> Vec<CandidateMatch> {
    let cache_key = format!("{}|{}|{}", ctx.url, ctx.host, ctx.path);

    if self.cache_enabled {
        if let Some(cached) = self.cache.read().peek(&cache_key) {
            return cached;
        }
    }

    let mut candidates = Vec::new();
    for (idx, rule) in self.rules.iter().enumerate() {
        if rule.is_disabled() { continue; }
        let match_result = rule.matcher.matches(&ctx.url, &ctx.host, &ctx.path);
        if match_result.matched || rule.is_negated() {
            candidates.push(CandidateMatch {
                rule_index: idx,
                captures: match_result.captures,
                is_negated: rule.is_negated(),
            });
        }
    }

    if self.cache_enabled {
        self.cache.write().insert(cache_key, candidates.clone());
    }
    candidates
}

fn apply_filter_gate(&self, candidates: &[CandidateMatch], ctx: &RequestContext) -> ResolvedRules {
    let mut result = ResolvedRules::new();
    let mut matched_protocols: HashMap<Protocol, bool> = HashMap::new();
    let active_skips = self.collect_active_skips_from(candidates, ctx);

    for cand in candidates {
        let rule = &self.rules[cand.rule_index];

        if cand.is_negated {
            // 否定规则原始匹配成功 → 标记协议已占
            if !cand.captures.is_none() { // matcher 原始匹配了
                matched_protocols.insert(rule.protocol, true);
            }
            continue;
        }

        if !rule.protocol.is_multi_match() && matched_protocols.contains_key(&rule.protocol) {
            continue;
        }

        // Filter gate: 基于当前请求上下文动态决策
        if !rule.include_filters.is_empty()
            && !Self::matches_all_filters(&rule.include_filters, ctx)
        {
            continue;
        }

        if Self::matches_any_filter(&rule.exclude_filters, ctx) {
            continue;
        }

        if rule.protocol != Protocol::Skip
            && Self::should_skip_rule(rule, &active_skips, &self.values, ctx)
        {
            continue;
        }

        if rule.protocol == Protocol::Skip {
            continue;
        }

        let resolved = ResolvedRule::new(rule.clone(), cand.captures.clone(), ctx, &self.values);
        result.add(resolved);

        if !rule.protocol.is_multi_match() {
            matched_protocols.insert(rule.protocol, true);
        }
    }
    result
}
```

## 数据结构变更

```rust
// 新增
#[derive(Debug, Clone)]
struct CandidateMatch {
    rule_index: usize,
    captures: Option<Vec<String>>,
    is_negated: bool,
}

// 修改缓存类型
// 旧: LruCache<String, ResolvedRules>
// 新: LruCache<String, Vec<CandidateMatch>>
```

## 兼容性

- `disable_cache()` 仍然生效（关掉 Phase A 缓存即可）
- `with_cache_capacity()` 不变
- `clear_cache()` 不变
- 外部 API（`resolve` 入参出参）完全不变
- 所有现有测试应继续通过（行为只有修正，无破坏）

## 测试计划

1. 原有 resolver 单元测试全部通过
2. 新增：两条同 matcher 不同 header filter，验证 Phase B 正确选路
3. 新增：无 header filter 的规则集，验证缓存仍命中（性能不回退）
4. 新增：negated 规则 + header filter 组合

## 风险评估

| 风险 | 可能性 | 缓解 |
|---|---|---|
| Phase A 少缓存 method → 命中率下降 | 低（同 url 不同 method 不多） | 监控缓存命中率 |
| negated 规则在 Phase B 的处理正确性 | 中 | 充分单元测试覆盖 |
| 重构后性能回退 | 低（filter 检查本身 O(n filter * 字符串比较)） | benchmark 对比 |

## 实现记录

### 用户目标验证清单

- 必须实现：`RulesResolver::resolve()` 改为两相执行，Phase A 只缓存 URL matcher 候选规则，Phase B 每个请求重新执行 includeFilter / excludeFilter / skip / first-match-wins / 模板展开。
- 必须实现：同一 URL、同一 pattern、同一协议下，多条 `includeFilter://h:x-tt-env-fe=...` 规则可以按当前请求 header 选中不同目标端口。
- 必须不破坏：无 filter 的规则仍复用 matcher 候选缓存；`disable_cache()`、`with_cache_capacity()`、`clear_cache()` 外部语义不变。
- 必须不破坏：negated 规则、skip 规则、multi-match 协议、模板变量展开和已有 filter 行为保持兼容。
- 必须真实验证：用 `bifrost-e2e` 启动真实代理和两个 mock upstream，请求同一 URL 时通过不同 `x-tt-env-fe` header 路由到不同 upstream。
- 必须交付：补充单元测试、E2E、human_tests 用例和索引，并执行两轮 Review/Fix/Test 闭环。

### 实现落点

- `crates/bifrost-core/src/rule/resolver.rs`
  - 新增 `CandidateMatch { rule_index, captures, is_negated }`。
  - `LruCache` 的 value 从 `ResolvedRules` 改为 `Vec<CandidateMatch>`。
  - `resolve()` 拆为 `get_matcher_candidates()` 与 `apply_filter_gate()`。
  - `collect_active_skips()` 改为 `collect_active_skips_from()`，基于 Phase A 候选集收集当前请求生效的 skip。
