# 变量冲突检测

## 背景

当用户为同一域名启用了多套规则（本地 My Rules + 多个 Group Rules）时，不同规则文件可能通过 markdown 代码块（例如 ` ```data `）定义了同名的内联变量，但值不同。规则合并阶段的变量表使用"先到先得"策略（`extract_inline_variables` + `entry(k).or_insert(v)`），后来的同名变量会被静默忽略，导致用户修改的值不生效却无法感知原因。

设计目标是在灵动岛（`RulesDynamicIsland`）上主动检测并展示跨规则文件的变量冲突，帮助用户在配置生效之前快速定位问题。当前实现已经把冲突检测集成到 `GET /api/rules/active-summary` 响应中，并在前端 Badge / 展开面板中做警告展示。

## 用户目标验证清单

### 必须实现

- `GET /api/rules/active-summary` 响应中包含 `variable_conflicts` 字段，形态为 `Vec<VariableConflict>`。
- 每个 `VariableConflict` 含 `variable_name` 和 `definitions: Vec<VariableDefinition>`，`VariableDefinition` 含 `rule_name`、`group_id`（`Option<String>`）、`value_preview`（截取前 80 字符）。
- 冲突判定：同一变量名在多个规则文件中出现，且至少存在两个不同的 `value`。全部相同则不算冲突。
- 检测范围包含本地 My Rules 和已启用的 Group Rules；两侧 `group_id` 分别为 `None` 与 `Some(<dir_name>)`。
- 前端 `RulesDynamicIsland`：当 `variable_conflicts.length > 0` 时 Badge 上叠加 `WarningOutlined`（`token.colorWarning`），展开面板顶部渲染冲突警告区（`token.colorWarningBg` 背景 + `token.colorWarningBorder` 边框）。
- 冲突区列出每个冲突变量名 `{var}` 及所有 definition（`rule_name` + `value_preview`），供用户跳转到相应规则文件修复。
- 单元测试覆盖同名不同值、同名同值、单规则文件、跨 Group Rules 四种场景。

### 必须不破坏

- `active-summary` 现有字段（`total`、`rules`、`merged_content`）保持向后兼容，`variable_conflicts` 为新增字段。
- 检测逻辑必须复用现有 `extract_inline_variables` / `extract_markdown_value_blocks`，不重复实现 markdown value block 解析。
- 检测只跑一次遍历（收集 var_map），不引入 O(N²) 逐对比较。
- 冲突展示只是可读警告，不阻断规则生效；用户仍可继续使用现有匹配。

### 必须真实验证

- Rust 单元测试：`test_detect_variable_conflicts_same_name_different_values`、`test_no_conflicts_when_values_match`、`test_no_conflicts_single_rule_file`、`test_conflicts_with_group_rules`、`active_summary_includes_local_group_rules_without_sync_session`。
- WebUI 真实浏览器：创建两个规则集使用相同变量名但不同值，观察灵动岛 Badge 出现警告图标，展开面板显示冲突列表。
- 单规则文件、变量值一致时冲突列表为空。

## 产品语义

### 冲突数据结构

```rust
struct VariableConflict {
    variable_name: String,          // 例如 "data"
    definitions: Vec<VariableDefinition>,
}

struct VariableDefinition {
    rule_name: String,               // 规则文件名，例如 "local-dev"
    group_id: Option<String>,        // None = 本地 My Rules；Some = Group Rules 目录名
    value_preview: String,           // truncate_preview(value, 80)
}
```

`value_preview` 是脱敏预览而非完整值，避免灵动岛面板出现超长内容或敏感信息全量泄露；用户看到冲突后跳转到规则文件本身查看和修复完整值。

### 检测算法

`active_summary` handler 在收集所有 enabled 规则时同时维护 `var_map: HashMap<String, Vec<InlineVarEntry>>`：

- `InlineVarEntry { rule_name, group_id, value }`。
- 每个规则文件调用 `extract_inline_variables(&rule.content)`，把每个变量 `(name, value)` push 到 `var_map[name]`。
- 全部收集完成后调用 `build_variable_conflicts(var_map)`：
  - 只保留 `entries.len() > 1` 且 `entries` 内至少存在两个不同 `value` 的键。
  - 每个键构造一个 `VariableConflict`，`definitions` 按 push 顺序保留，方便前端稳定展示。

### 前端展示

`web/src/pages/Rules/RulesDynamicIsland.tsx`：

- 状态：`const [variableConflicts, setVariableConflicts] = useState<VariableConflict[]>([])`。
- 每次拉取 `getActiveSummary()` 时 `setVariableConflicts(resp.variable_conflicts ?? [])`。
- Badge 层：当 `variableConflicts.length > 0` 时叠加 `<WarningOutlined>`，`Tooltip` 提示 `${n} variable conflict${n > 1 ? "s" : ""}`。
- 展开面板：`activeRules.length > 0 || variableConflicts.length > 0` 时展开；顶部渲染冲突区（`token.colorWarningBg` 背景 + `token.colorWarningBorder` 边框 + `token.colorWarning` 文本），列出 `{conflict.variable_name}` 与 definitions。
- 空态：`activeRules.length === 0 && variableConflicts.length === 0` 才显示"暂无生效规则"提示。

## 技术细节

### 关键文件

- `crates/bifrost-admin/src/handlers/rules.rs`
  - `ActiveSummaryResponse { total, rules, variable_conflicts, merged_content }`。
  - `VariableConflict` / `VariableDefinition` 结构定义。
  - `InlineVarEntry`（内部）。
  - `active_summary(state)`：入口，路由 `/api/rules/active-summary`。
  - `collect_enabled_from_storage(storage, group_id, group_name, var_map, content_parts)`：分别对本地和每个 Group 目录调用，累积 `var_map`。
  - `build_variable_conflicts(var_map)`：判定与预览截断。
  - `truncate_preview(value, 80)`：Unicode-safe 截断。
- `crates/bifrost-core/src/rule/parser/mod.rs`
  - `extract_inline_variables(text) -> HashMap<String, String>`：调用 `extract_markdown_value_blocks` 收集 markdown value block。
  - `extract_markdown_value_blocks`：内部函数（同 crate 使用即可，不需要 pub）。
- `web/src/api/rules.ts`：TypeScript 类型 `VariableConflict`、`VariableDefinition`、`ActiveSummaryResponse`。
- `web/src/pages/Rules/RulesDynamicIsland.tsx`：Badge + 展开面板冲突区。

### 冲突判定示例

```rust
let mut var_map: HashMap<String, Vec<InlineVarEntry>> = HashMap::new();
var_map.entry("data".into()).or_default().push(InlineVarEntry {
    rule_name: "rule-a".into(), group_id: None, value: "x-tt-env: boe_xxx".into()
});
var_map.entry("data".into()).or_default().push(InlineVarEntry {
    rule_name: "rule-b".into(), group_id: None, value: "x-debug: true".into()
});
let conflicts = build_variable_conflicts(var_map);
assert_eq!(conflicts.len(), 1);
assert_eq!(conflicts[0].variable_name, "data");
```

## Sync 边界

- 变量冲突检测是运行时诊断结果，不落盘、不参与 sync。
- Group Rules 内容本身参与 sync；同步下来的 Group 变量与本地变量若冲突会在下一次 `active-summary` 拉取时被检测出来。
- `value_preview` 只在 API 响应体中出现，不写入任何持久化文件；避免变量原文经导出/日志外泄。

- `active_summary` handler 输出 `variable_conflicts`。

- `RulesDynamicIsland` Badge 叠加 `WarningOutlined`。
- 展开面板顶部冲突区（Ant Design token 颜色）。
- 空态判定合并 `variableConflicts.length`。

### Phase 3：Group 覆盖

- `active_summary` 遍历每个 valid group 目录，`group_id/group_name` 正确回填。
- 单元测试 `test_conflicts_with_group_rules`：本地与 Group 混合触发冲突。

### Phase 4：可选扩展

- CLI `bifrost rule active` 输出 `variable_conflicts` 摘要。
- 灵动岛跳转到冲突规则文件的编辑器锚点。
- 支持 hide/mute 某个冲突（用户已确认）。

## 风险与决策点

- `value_preview` 截 80 字符可能仍暴露敏感信息（token/密钥）。后续可以引入按规则或按变量名的脱敏配置。
- 检测粒度是"变量名 + 值"，不识别语义等价（例如 `"a"` vs `a` 或 `Header: v` vs `header: v`）。这类误报/漏报按简单字符串比较处理，避免复杂语义规则。
- 变量冲突警告不阻断请求代理；用户可能忽略警告继续调试。若产品希望"冲突时提示更强"，可扩展为 CLI 状态码或 tray 图标气泡。
- Group Rules 数量非常大时 `active-summary` 单次响应体积可能很大；`variable_conflicts` 属于附加字段，需要留意在前端做懒加载或分页展开。
- 当前 `extract_markdown_value_blocks` 只是 crate 内部函数（非 `pub`），如果未来其他 crate（例如 `bifrost-cli`）也要复用冲突检测，需要显式导出。
